# Alert rules and observability rollout — runbook

**Date:** 2026-09-11 · **Companion to:** `docs/plans/2026-09-11-001-feat-observability-hardening-plan.md` (R22) and the review `01-review-2026-08-30.md`.

This is the operator half of the observability work: the Grafana alert rules (golden path — rules are created in the UI at [grafana.entur.org](https://grafana.entur.org), so this file is the reviewable definition they are created from), the Slack route they notify through, and the rollout checklist for the pieces that cannot run from CI. Every `kix_*` metric named here is declared in `disruptions/api/metrics.py`; if a name here does not grep there, this file is stale — fix whichever is wrong before creating rules.

## Ground rules (from Entur's alerting guide)

- Create rules in the **team folder `team-ki-eksperimentering`** at grafana.entur.org, data source **`prometheus-thanos`**. The folder was created on 2026-09-15; Entur's alerting guide says each team owns one and to create it if it is missing, named **after the team and not after a service** — one folder holds the rules for everything the team operates, so a `kix-avvik` folder would be the wrong shape. The `team-` prefix and the dashes are the convention the other teams' folders follow, read off the folder list. That one source covers every cluster. There is no per-environment Prometheus: a query picks its environment with `prometheus_group`.
- **Every rule notifies `#alerts-kix` in Slack, through the `alerts-kix` contact point the rule selects itself** (checklist step 6). No PagerDuty: the team decided on 2026-09-11 not to register a PagerDuty team, so the golden path's `entur-pagerduty` route has nobody at its end. A rule that falls through to it reaches no one.
- **Every rule is titled with its environment first**, `[dev] Poller stopped` / `[prd] Poller stopped`, the uptime policy's convention. dev and prd share one channel, and distinct titles also keep Grafana from grouping the two copies into one message.
- Every rule carries the labels **`service_name: kix-avvik`**, **`env`** (`dev`/`tst`/`prd`) and **`severity`** (`critical`/`warning`). They route nothing now; they are what a reader filters on. **`critical` means "look at this first", not "someone is woken up"**: nothing pages and nothing escalates, at any hour. That is the trade the team chose. An experiment with no SLA has no on-call.
- Every PromQL below needs selectors added; they are omitted for readability. **The namespace label depends on where the metric comes from** (measured in dev on 2026-09-11):
  - `kix_*`, our app's metrics, scraped from our pod: `kubernetes_namespace="kix-avvik"`.
  - `kube_*`, from kube-state-metrics (rules 3–5): **`exported_namespace="kix-avvik"`**. Prometheus scrapes kube-state-metrics like any other pod, so the series' own `namespace` label is `prometheus`, where kube-state-metrics runs, and `namespace="kix-avvik"` matches nothing. Entur's alerting guide gets this wrong in its examples.
  - `container_*`, from the kubelet's cAdvisor (rule 4): `namespace="kix-avvik"`.
  - Every query also needs `prometheus_group="kub-ent-dev-001"` for a dev rule or `"kub-ent-prd-001"` for a prd rule.

  A wrong label raises no error. The query returns no data, and a rule built on it never fires.
- Alert on symptoms; every rule here has a response (see "response" column notes).

## Rules

| # | Alert | PromQL (add selectors) | Condition / `for` | Severity | Notes |
|---|---|---|---|---|---|
| 1 | Poller stopped | `time() - kix_poller_last_tick_timestamp_seconds > 900` | 5m | critical | The tick heartbeat moves every ~60 s regardless of upstream; 15 min of silence means the poller (or the pod) is gone and `/health` self-healing did not recover it. **No-data → Alerting** (scrape loss and pod death must alert, not go silent). Do NOT build this on the cycle gauge — cycles are event-driven and pause on quiet nights. |
| 2 | Rebuild stale (observation) | `time() - kix_poller_last_cycle_timestamp_seconds > 3600` | 15m | warning | Cycle freshness, not liveness: legitimate on quiet nights, so this is a daytime-attention rule, not an urgent one. Consider muting outside 05:00–24:00. |
| 2a | Subscription mirror stale | `time() - (time() - kix_mirror_age_seconds) > 900` — or simply `kix_mirror_age_seconds > 900` | 15m | warning | **U6, 2026-09-12.** The poller matches webhook subscriptions against an in-memory mirror kept current by a watermark query, so a mirror that stops syncing keeps alerting a recipient whose client revoked it and keeps missing every new one — with the cycle, the pushes and every other rule looking perfectly healthy. 900 s is about three median cycle periods (~296 s), i.e. a sync that has failed a few times rather than one slow cycle. **No-data → OK**, deliberately: the gauge is absent until the first sync completes (the restart window) and in every deployment with the channel off, which is tst. The number that matters for CORRECTNESS is a different one and is enforced in code, not here — past `notification_store.MIRROR_MAX_AGE_S` (6 h) the store re-seeds itself, because a revocation arrives as a tombstone whose own TTL deletes it after ~24 h, so a sync broken longer than that loses the removal for good. This rule is the warning; that constant is the guard. |
| 2b | Worker stopped | `time() - kix_worker_last_tick_timestamp_seconds > 900` | 5m | critical | **U11, 2026-09-13.** Rule 1 for the delivery worker, which is its own Deployment (`kix-avvik-worker`) from the same image. Its tick moves on EVERY round, including the ones that find nothing to deliver, so a quiet night must not go stale — a heartbeat tied to work delivered would page for a worker behaving perfectly. **No-data → Alerting**, and here that is not the copied habit it is on rule 1: the series is absent from the API pods entirely, so a worker scaled to zero, a release rolled back, or a values file that stopped rendering a Deployment all show up as no data and would otherwise read as healthy. It stays silent where no worker is deployed only if the rule carries an environment selector — tst renders no worker at all, so scope this rule to the environments that have one. |
| 2c | Delivery backlog | `kix_delivery_backlog_age_seconds > 1800` | 15m | warning | **U11, 2026-09-13.** How long ago the oldest DELIVERABLE pending delivery was minted, as of the worker's last round. An event is valid for one hour, so 1800 s is the halfway point: past it the backlog is heading for expiry rather than merely lagging, and the response is replicas (`deployment.forceReplicas` in the worker values file — see the drain formula in `docs/operations/notification-webhooks.md`). Deliverable is the operative word and is what keeps this rule about the QUEUE: rows held by a lease, rows inside U7's durable backoff and rows past a destination's per-cycle ceiling are all absent from it, so one unwell receiver cannot drive it — that shows up as `throttled` and `backed_off` on `webhook_delivery_round` instead. **No-data → OK**: the gauge is absent wherever no worker runs, and it reads 0 on an empty queue, which is the ordinary state. |
| 3 | Pod restarts | `increase(kube_pod_container_status_restarts_total[15m]) > 3` | 0m | warning | More than 3 restarts in 15 min — includes the new liveness restarts, so a flapping `/health` shows up here (crash-loop guard: `HEALTH_STALE_AFTER_S=0` disables the staleness branch via a values-only deploy). |
| 4 | Memory near limit | `sum by (pod) (container_memory_working_set_bytes{container!=""}) / sum by (pod) (kube_pod_container_resource_limits{resource="memory"}) > 0.85` | 5m | critical | prd limit is ~2457 Mi; OOM kill on the single replica is a full outage. The two halves take **different** namespace labels (`namespace` on `container_*`, `exported_namespace` on `kube_*`); `sum by (pod)` joins them on the pod name. |
| 5 | Pod not ready | `kube_pod_status_ready{condition="true"} == 0` | 3m | critical | With one replica, not-ready = the service is down. `/health` 503s (dead/stale poller) land here too. |
| 6 | ERROR logged | `increase(kix_log_records_total{level="ERROR"}[10m]) > 0` | 0m | warning | The ERROR channel is deliberately near-silent (verified clean pre-rollout), so any ERROR is worth a look. `labelling_stale`, `thread_died` and `health_degraded` all arrive here. |
| 7 | Push failures | `sum(increase(kix_push_total{result="error"}[30m])) / sum(increase(kix_push_total[30m])) > 0.2 and sum(increase(kix_push_total[30m])) > 5` | 10m | warning | Ratio with a volume guard — single-push blips at low volume must not fire. `gone` is not an error (device unsubscribed). |
| 8 | LLM wording failures | `sum(increase(kix_llm_message_total{surface="live",result=~"error\|unavailable\|truncated"}[30m])) / sum(increase(kix_llm_message_total{surface="live"}[30m])) > 0.3 and sum(increase(kix_llm_message_total{surface="live"}[30m])) > 5` | 10m | warning | **`surface="live"` only** — `/meldinger` replay bursts of `ungrounded` are the expected product of prompt work and must not fire. Travellers get the deterministic template on failure, so this is quality degradation, not outage. |
| 9 | Labelling stale | `time() - kix_labelling_last_success_timestamp_seconds > 172800 and sum(increase(kix_decision_write_total{result="ok"}[48h])) > 0` | 30m | critical | 48 h without successful labelling **while decisions were still being written** — unlabelled decisions become permanently unknown after 10 days. **No-data → OK**, deliberately: the gauge is absent until something has been labelled at all, which is the normal state of a fresh deployment and of tst, and alerting on it would fire precisely where the in-app detector stays quiet on purpose. The work gate is the metric-side echo of that detector's own gate; the two windows differ slightly (this one: decisions written in 48 h; in-app: decisions whose `call_date` is 2-10 days old), which is fine for a belt-and-braces rule beside rule 6's primary. |
| 10 | 5xx rate | `sum(rate(kix_http_requests_total{status="5xx",path!="health"}[5m])) / sum(rate(kix_http_requests_total{path!="health"}[5m])) > 0.05` | 5m | critical | **`path!="health"` is load-bearing**: a stale-poller window emits ~24 deliberate `/health` 503s per minute, and without the exclusion this rule double-fires beside rules 1/5. |
| 11 | p99 latency | `histogram_quantile(0.99, sum by (le) (rate(kix_http_request_duration_seconds_bucket{path!="health"}[5m]))) > 5` | 10m | warning | Golden-path default threshold; tune after observing real traffic. |

Suggested rollout order: rules 3–5 first (platform metrics only, zero app dependency — they work before the app metrics land), then 1, 6, 9, 10 once the metrics-arrival check below passes, then 2, 2b, 2c (only in environments where the worker release is deployed), 7, 8, 11.

## Rollout checklist (operator steps, in order)

1. **Metrics arrival: PASSED in dev on 2026-09-11. Repeat for prd before creating any prd rule.** In Grafana → **Explore**, data source `prometheus-thanos`, query `count by (__name__) ({__name__=~"kix_.*", kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"})`. dev returned 27 metric names, exactly what the 12 metrics in `metrics.py` expose once each histogram's `_bucket`/`_count`/`_sum`/`_created` and each counter's `_created` are counted. For prd, use `kub-ent-prd-001`. If nothing returns, check the pod annotations (`kubectl get pod -n kix-avvik -o jsonpath='{.items[0].metadata.annotations}'` should show `prometheus.io/scrape: "true"`, `path: /metrics`, `port: "9464"`), then whether annotation-based discovery is active for this namespace (ask `#talk-utviklerplattform` if not — PodMonitor CRDs would be the alternative). Rules created on absent series silently never fire.
2. **IAM verification (per environment, after `entur apply` lands the manifest change):**
   ```sh
   gcloud projects get-iam-policy ent-kixavvik-<env> \
     --flatten=bindings[].members --filter='bindings.role:roles/cloudtrace.agent OR bindings.role:roles/telemetry.tracesWriter'
   ```
   Expect `application@ent-kixavvik-<env>.iam.gserviceaccount.com` under at least one of the two roles (both were granted; the platform filter drops silently). **Verify before flipping `TRACING_ENABLED` on, not after.** Tracing fails open for the app — no push is ever lost to an export problem — but the export is not quiet: the OTLP exporter logs `Failed to export` at **ERROR per failed batch**, roughly one every 5 s, and `PERMISSION_DENIED` (no role) and `UNAVAILABLE` (service not enabled) are both non-retryable, so it never stops. Every one is counted by `kix_log_records_total{level="ERROR"}` — rule 6 — so an unprovisioned environment fires continuously and buries `labelling_stale`, `thread_died` and `health_degraded`. This is why the flag shipped `"false"` in tst and prd.
3. **Trace smoke (dev):** dev ships with `TRACING_ENABLED=true`; tst and prd shipped `"false"`, each to be flipped by a values-only dispatch deploy only after step 2 passes **for that project** — which it did for all three on 2026-09-11. **prd was flipped to `"true"` the same day**, after step 2 was re-run for `ent-kixavvik-prd`; tst stays `"false"`. The inbound-`traceparent` question that also gated prd was **settled the same day** (risk accepted, referred to Team Plattform as a shared-ingress concern; see the residual review findings), so step 2 is now the only gate. One consequence to carry into any later reading of prd's traces: a caller can still force prd's request sampling to 0 % or 100 %, so **request-span volume is not evidence of anything** there. Poller-cycle traces have no inbound parent and are the sound basis for a coverage claim. With tracing on, make one request to `https://kix-avvik.dev.entur.io/impact?...` (any traced route), then open Trace Explorer in **`ent-kixavvik-dev`** (the app project — not `ent-kub-dev`; if empty, check both, the platform docs disagree) and filter `service.name="kix-avvik"`. A poller-cycle trace (root span `poller_cycle` with phase children) should appear within minutes of the next SIRI-SX movement.
4. **tst/prd terraform:** the PR plan validated dev only. On the `terraform.yml` dispatch runs for tst and prd, review the plan step before apply: tst must show the uptime check **without** a notification channel; prd with one.
5. **Uptime alert routes (dev and prd).** The uptime policy notifies `#alerts-kix` in Slack in dev and prd, plus email until `uptime_notification_email` is set to `""`. tst has the check and no policy: the team dropped it from the routing on 2026-09-11, and its host does not resolve anyway (tst is not deployed), so any route there would open an alert on its first dispatch and keep it open.
   - **Slack, BEFORE that environment's Terraform runs:** in the project's console, **Monitoring → Alerting → Notification channels → Slack → Add new**, authorize the Entur workspace, pick `#alerts-kix`, and **click Save**. The display name is free; the Terraform finds the channel by the Slack channel it posts to (`uptime_slack_channel` in that environment's tfvars), so there is nothing to type exactly. Once per project — dev and prd. If `#alerts-kix` is private, invite the Google Cloud Monitoring app to it. Allow popups for `console.cloud.google.com` first: a blocked popup fails the Slack authorization with "Unable to retrieve the temporary verification code".
   - **Then check it was saved, then test it.** The dialog will send a test notification *before* Save, so a message in `#alerts-kix` proves nothing on its own — the first dev channel was tested, never saved, and did not exist. Confirm it with `gcloud alpha monitoring channels list --project=ent-kixavvik-<env> --format='value(type,labels.channel_name,displayName)'` (a `slack` row with `#alerts-kix`), then **Send test notification** on the saved channel. The Terraform lookup proves the channel exists; only the test proves it delivers.
   - **Email (dev and prd, after the apply):** send a mail to the `uptime_notification_email` in that environment's tfvars and confirm it arrives, then check the channel in **Cloud Monitoring → Alerting → Notification channels** — Google marks a channel whose mail bounced. Nothing upstream of this checks it: Terraform accepts any string and Google accepts any address, so a bad one applies clean and reads healthy while every alert is lost at the moment it fires. This step exists because the address originally committed here (`sg-dig-team-ki-eksperimentering@entur.no`) did exactly that — it is the team's **Google group**, a real IAM principal but not a mailbox, and it bounced with "wasn't found at entur.no". The working alias is `Team-KI-eksperimentering@entur.org`; the two strings are different on purpose.
6. **Alert route: the Grafana Slack contact point `alerts-kix`. Decided 2026-09-11, created 2026-09-15. Still owed: the route test below, BEFORE step 7** — the contact point's own **Test** button has fired, no rule has, and those are different things. On Entur's golden path, rules route through the shared `entur-pagerduty` contact point to a **PagerDuty team**, and PagerDuty posts to that team's Slack channel. This team has no PagerDuty team manifest, and on 2026-09-11 it decided not to create one: a manifest brings an on-call rotation whose escalation reaches outside working hours, and this experiment has no SLA. Entur's guide prefers PagerDuty over a Grafana Slack contact point so that Slack posts cannot drift from PagerDuty's view of an incident. With no PagerDuty team, there is nothing to drift from. The alerts go to **`#alerts-kix`**, beside the uptime alerts (step 5).
   - **Check that you can create a contact point.** Satisfied on 2026-09-15. In grafana.entur.org, open **Alerting → Contact points**. If **+ Add contact point** is missing or greyed out, your Grafana role does not allow it. The role comes from Entra, not from Grafana itself, so ask Team Kvalitet, which runs grafana.entur.org (`entur/grafana`), for it.
   - **The Slack credential was the one open question and it is answered: there is nothing for this team to hold.** A Slack contact point needs either an incoming-webhook URL for `#alerts-kix` or a bot token plus the channel, and Entur's documentation did not say how a team gets either (searched 2026-09-11) — but **grafana.entur.org already has a Slack app that contact points use**, so `alerts-kix` was created on 2026-09-15 without a team-created webhook or token. The `#talk-utviklerplattform` question is closed, and so is the rotation exposure: no secret of ours exists in the contact point, this repo, a tfvars file or a GitHub secret. **That last rule still binds any contact point that does carry its own URL or token** — Team Sikkerhet treats an exposed Slack webhook as an incident that needs rotating (SIK-1650, SIK-1692). If `#alerts-kix` is private, invite the Slack app to it.
   - **One contact point, `alerts-kix`, serving dev and prd — it exists since 2026-09-15.** In **Alerting → Contact points** it is the receiver whose edit URL ends in `YWxlcnRzLWtpeA`, which is the name base64-encoded; that is how Grafana addresses a receiver, so the URL changes if the contact point is ever renamed. The default Slack title is `[FIRING:1] <alert name> …`, so the `[dev]`/`[prd]` rule titles (ground rules) come right after Grafana's status tag without a custom template. If that tag gets in the way, a one-line **Title** template on the contact point removes it.
   - **Route on each rule, not through the notification policy tree.** In each rule's notification section, choose **Select contact point** and pick `alerts-kix`, not **Use notification policy**. The policy tree is org-wide and shared. Entur's alerting guide describes it routing on `service_name` to `entur-pagerduty` (the actual tree was not inspected), the first matching policy wins, and this team owns neither the order nor the default policy's contact point. So a child policy in the wrong place, or an alert that matches none, lands on a PagerDuty route with no team behind it, silently. A contact point picked on the rule bypasses the tree, and the route is visible on the rule itself.
   - **Test the route, not the contact point. This is what is still owed as of 2026-09-15.** The contact point's **Test** button sends whatever is in the form, saved or not — it has been pressed and it proves only that the Slack app can post. That is the trap the Cloud Monitoring dialog set in step 5, and it tests neither the routing nor the rule title. Instead, in the `team-ki-eksperimentering` folder, create a throwaway rule titled `[dev] route test`: query `vector(1)`, threshold above 0, pending period 0, labels `env=dev` and `severity=warning`, contact point `alerts-kix`. Confirm that it lands in `#alerts-kix` within a few minutes with `[dev]` leading, then delete the rule. If it does not arrive, no real rule will either. An untested route is the same silent failure as the uptime email address that bounced (step 5).
7. **Grafana rules:** once step 6's test alert has landed, create the table above in the `team-ki-eksperimentering` folder, dev first, then prd. Each rule gets its `[env]` title, its three labels and the **Select contact point** route to `alerts-kix`. Check the route on every rule before saving: a rule left on **Use notification policy** goes through the shared tree (step 6).

## What this deliberately does not cover

- SLOs/SLODash (no SLA on this experiment).
- PagerDuty and on-call: declined on 2026-09-11 (step 6). Nothing here pages or escalates.
- Grafana-as-code: rules stay UI-managed per the golden path; this file is their reviewable source of truth.
- The uptime check's alerting lives in Terraform (`terraform/monitoring.tf`), not Grafana — GCP uptime checks are invisible to Thanos.
