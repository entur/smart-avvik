# Alert rules and observability rollout — runbook

**Date:** 2026-09-11 · **Companion to:** `docs/plans/2026-09-11-001-feat-observability-hardening-plan.md` (R22) and the review `01-review-2026-08-30.md`.

This is the operator half of the observability work: the Grafana alert rules (golden path — rules are created in the UI at [grafana.entur.org](https://grafana.entur.org), so this file is the reviewable definition they are created from), the Slack route they notify through, and the rollout checklist for the pieces that cannot run from CI. Every `kix_*` metric named here is declared in `disruptions/api/metrics.py`; if a name here does not grep there, this file is stale — fix whichever is wrong before creating rules.

## Ground rules (from Entur's alerting guide)

- Create rules in the **team folder `team-ki-eksperimentering`** at grafana.entur.org, data source **`prometheus-thanos`**. The folder was created on 2026-09-15; Entur's alerting guide says each team owns one and to create it if it is missing, named **after the team and not after a service** — one folder holds the rules for everything the team operates, so a `kix-avvik` folder would be the wrong shape. The `team-` prefix and the dashes are the convention the other teams' folders follow, read off the folder list. That one source covers every cluster. There is no per-environment Prometheus: a query picks its environment with `prometheus_group`.
- **Every rule notifies `#alerts-kix` in Slack, through the `alerts-kix` contact point the rule selects itself** (checklist step 6). No PagerDuty: the team decided on 2026-09-11 not to register a PagerDuty team, so the golden path's `entur-pagerduty` route has nobody at its end. A rule that falls through to it reaches no one.
- **Every rule is titled with its environment first**, `[dev] Poller stopped` / `[prd] Poller stopped`, the uptime policy's convention. dev and prd share one channel, and distinct titles also keep Grafana from grouping the two copies into one message.
- Every rule carries the labels **`service_name: kix-avvik`**, **`env`** (`dev`/`tst`/`prd`) and **`severity`** (`critical`/`warning`). They route nothing now; they are what a reader filters on. **`critical` means "look at this first", not "someone is woken up"**: nothing pages and nothing escalates, at any hour. That is the trade the team chose. An experiment with no SLA has no on-call.
- **The queries in the rule sections below are already written out with their selectors** — this bullet is the rule behind them, and what a new rule has to follow. **The namespace label depends on where the metric comes from** (measured in dev on 2026-09-11):
  - `kix_*`, our app's metrics, scraped from our pod: `kubernetes_namespace="kix-avvik"`.
  - `kube_*`, from kube-state-metrics (rules 3–5): **`exported_namespace="kix-avvik"`**. Prometheus scrapes kube-state-metrics like any other pod, so the series' own `namespace` label is `prometheus`, where kube-state-metrics runs, and `namespace="kix-avvik"` matches nothing. Entur's alerting guide gets this wrong in its examples.
  - `container_*`, from the kubelet's cAdvisor (rule 4): `namespace="kix-avvik"`.
  - Every query also needs `prometheus_group="kub-ent-dev-001"` for a dev rule or `"kub-ent-prd-001"` for a prd rule.

  A wrong label raises no error. The query returns no data, and a rule built on it never fires.
- Alert on symptoms; every rule here has a response (see "response" column notes).

## Rules

**A dashboard of these rules is generated from this file.** `scripts/make_alert_dashboard.py`
parses the sections below — query, threshold, pending period, description — into
`alert-dashboard.json` beside it: one timeseries panel per rule with its threshold drawn as a line,
and the dev/prd pair collapsed onto an `env` variable, since the only difference is
`prometheus_group`. Import it at Dashboards → New → Import. A panel reading *No data* is the silent
failure this file is written against, made visible. Re-run the script after editing a rule below.


Each rule has a section below carrying the exact query, condition, pending period, no-data setting
and annotations to type into Grafana. **The queries are written out for `dev`; the only edit for prd
is `prometheus_group="kub-ent-prd-001"`.** The selector rules in the ground rules above are why they
look as they do; they are expanded here because assembling them by hand is where the silent failure
lives.

**Paste every query into Explore and confirm it returns a value before you create the rule.** The
label names were measured once, on 2026-09-11, and are derivable from nothing in this repo. A query
whose selectors are wrong returns no data, raises no error, and yields a rule that can never fire —
a ten-second check per rule prevents the one failure this whole file is written against.

Every rule carries the three labels from the ground rules — `service_name: kix-avvik`, `env`, and
the section's own `severity` — and routes with **Select contact point → `alerts-kix`**. Set the
error branch ("Alert state if execution error or timeout") to **Error** everywhere, the editor's
default for a new rule: a query this repo cannot evaluate is itself worth saying out loud. This
sentence said **Alerting** until 2026-09-23. The importer sets **Normal** (`OK` on the wire), and all
25 imported rules carried it until that day. The no-data branch is per rule
and is stated in each section; Grafana's **Normal** is what the notes below call OK.

**Grafana reduces before it compares** — the route test's `Value: A=1, C=1` is the query, a Reduce
and a Threshold. Eleven of these return a single value already (`sum()`, `max()`,
`histogram_quantile`) and pass through it harmlessly, but rules **3, 5 and 6 return one series per
pod on purpose**, so that the alert names the pod that is restarting or logging. Those three need
**Reduce: Last** set explicitly; Mean over a per-pod series is a different question than the one the
rule asks.

**Three shapes here are deliberately not the one-liner they look like, and all three were measured
on 2026-09-15 against the running pods.** Read these before editing any query.

1. **`max()` wraps every unlabelled gauge, and removing it breaks the rule.** Both Deployments
   export **every** metric name: `metrics.py` registers all of them with the default registry at
   import, both `kix-avvik` and `kix-avvik-worker` run that module and both pods are scraped
   (`prometheus.io/scrape: "true"`, port 9464, verified in dev and prd) — and an unset
   `prometheus_client` gauge exports as **`0`**, not as absent. Measured on the dev pods: the worker
   serves `kix_poller_last_tick_timestamp_seconds 0.0` and `kix_poller_last_cycle_timestamp_seconds
   0.0`, the API serves `kix_worker_last_tick_timestamp_seconds 0.0`. Unaggregated, rules 1, 2 and 2b
   each match the *other* Deployment's zero, compute `time() - 0` ≈ 57 years, and fire forever. The
   aggregation also fixes what no-data means: with `max()`, no data is "every pod is gone", which is
   the state those rules want to alert on. **`WORKER_LAST_TICK`'s own docstring claims the series is
   "absent from the API pods entirely" — that is false**, and it is the sentence that produced the
   original rule. A labelled counter behaves the other way and needs no aggregation: no child series
   exists until the first increment, which is why rules 6–10 select rather than aggregate away.
2. **Rule 9's `and` must be `and on()`.** PromQL matches `and` on identical label sets. Its left side
   carries the series' own labels while the right side, after `sum()`, carries none, so a bare `and`
   matches nothing and the rule can never fire in either direction — the vacuous-guard shape this
   repo has been bitten by before. Rules 7 and 8 never had the problem because both of their sides
   are already `sum()`s with empty label sets.
3. **Rule 2a could not be created until its metric was replaced** (2026-10-13). See its section.

### 1 — Poller stopped · critical

```promql
time() - max(kix_poller_last_tick_timestamp_seconds{kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"})
```

**Condition** IS ABOVE `900` · **pending** `5m` · **no data → Alerting**

- `summary`: `The poller heartbeat has stopped (dev)`
- `description`: `No poller tick for 15 minutes. The tick moves every ~60 s regardless of upstream, so this is the thread or the pod rather than a quiet night, and /health's self-healing did not recover it. Check the pod; a restart is the usual response.`

No data must alert here: scrape loss and pod death are exactly what this rule is for. Do **not**
build it on the cycle gauge — cycles are event-driven and pause legitimately on quiet nights. The
`max()` is load-bearing (see the note above). Startup is covered: measured 2026-09-15, container
start to Ready is **29 s in dev and 24 s in prd**, well inside the 5m pending period — but the gauge
reads 0 from process start until the first tick, so a pathological startup (KTD2 documents up to
~300 s of BigQuery loads) would fire this on a deploy.

**Since the poller lease (2026-10-13) this rule means "no pod at all", not "no poller".** Every API
pod runs the loop and beats, the followers included, so `max()` stays fresh while any pod lives,
however the cycle is doing. A pod that is alive and leads nobody is rule 1a's.

### 1a — No poller leader · critical

```promql
sum(kix_poller_leader{kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"})
```

**Condition** IS BELOW `1` · **pending** `5m` · **no data → Alerting** · **error → Error**

- `summary`: `No pod holds the poller lease (dev)`
- `description`: `No API pod has led for 5 minutes: no rebuild cycle, no push, no webhook emit, no labelling check. The pods still serve the last-built tables, so reads look healthy while refreshed_at ages. Expected and self-clearing after a SIGKILLed or crashed leader: the successor waits out the 300 s lease TTL plus one 60 s tick, which is longer than this rule's pending window, so a forced kill fires it once. Otherwise look at event="poller_lease" records in ent-kub-<env> namespace kix-avvik (acquire_failed and error mean the Firestore notifications database is failing; refused means some holder's held_until is still in the future) and at /ready's role on each pod. Never delete the lease document. Runbook: docs/operations/poller-lease.md.`

**Hand-built, never imported**: query `A` is the expression above, threshold `C` reads `A` with
`reducer: last` inside `C` and compares `< 1` — the shape Export shows for rule 1, and the one the
importer's `prometheus_math` node cannot produce (see "How the rules were actually created"). No data
must alert: `sum()` over no series is no data, which is "no API pod is being scraped", and that is a
state this rule is also for (it overlaps rule 1 there, deliberately — rule 1 cannot see a live pod
that leads nobody, and this rule cannot tell a dead pod from a scrape gap). **Create it in dev and prd
only.** tst has no lease backend, every tst pod exports the gauge as 0, and the rule would fire
forever.

**What fires it, and what does not.** A graceful handoff — a deploy's SIGTERM, a scale-in, an
operator deleting the leader pod — releases the lease, and the next follower tick acquires: seconds
of zero, well inside 5m. A leader that dies without releasing (OOM kill, SIGKILL past the 270 s grace,
a node lost) costs the TTL plus a tick, ~6 minutes, so it fires once and resolves by itself; that is
correct and is the only signal a cold handoff gives. At one replica a WEDGED leader keeps its gauge at
1 (nothing clears it until the thread reaches a boundary), so this rule stays quiet until liveness
restarts the pod at `HEALTH_STALE_AFTER_S` (600 s) — then it reads 0 through the restart, the startup
and the first tick, and may fire. A Firestore outage longer than ~5 minutes fires it in every
environment, because no pod can renew or acquire (runbook: "Firestore outage").

### 1b — Two poller leaders · critical

```promql
sum(kix_poller_leader{kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"})
```

**Condition** IS ABOVE `1` · **pending** `1m` · **no data → Normal** · **error → Error**

- `summary`: `More than one pod believes it holds the poller lease (dev)`
- `description`: `Two pods have each reported leading for over a minute. The gauge is each pod's own belief, so this is two pods that BOTH think they lead, which a stalled leader does until its next boundary or tick: tolerated for less than the pending minute during a handoff after a stall, and a firing is not. Both may be rebuilding the same tables and pushing the same alerts. Check event="poller_lease" (acquired on one pod, lost or lease_lost on the other) and the duplicate check over event="push" result="sent" per journey and situation. If it persists, delete the stalled pod — the one whose own series reads 1 while its /ready answers role follower (its local deadline has passed; only the gauge has not caught up) — never the lease document. Runbook: docs/operations/poller-lease.md.`

Same expression and the same hand-built shape as 1a (query `A`, threshold `C` with `reducer: last`,
here `> 1`). No data is **Normal**: rule 1a owns absence. **What it measures is belief, not writes.**
The gauge is set after `on_acquire` succeeds and cleared on loss, a failed acquisition and shutdown,
and a leader only notices a loss at its next tick — so a leader whose thread stalled past the TTL
still reads 1 while the follower that acquired its lapsed lease also reads 1. The fences stop the
stalled one at its next boundary (it issues no further `CREATE OR REPLACE` and submits no further
push), and the store-side pre-send check refuses a push the other has already marked; the sum then
returns to 1 at that pod's next tick. A dip above 1 shorter than the minute is that sequence and is
expected; a firing is a stall longer than a minute past the TTL, which the plan's AE9 and U9's stop
criterion (`docs/plans/2026-10-13-001-feat-zero-downtime-deploy-autoscaling-plan.md`) treat as a
defect — both read the firing, never the instantaneous sum. **The worker pod exports the name as 0** (rule 1's `max()` note) and
so do followers, which is why this is a `sum()` and never a `count()` — and why the dashboard panel
draws both: `count()` is how many pods export the gauge (the API pods plus the worker), `sum()` is
how many lead.

### 2 — Rebuild stale · warning

```promql
time() - max(kix_poller_last_cycle_timestamp_seconds{kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"})
```

**Condition** IS ABOVE `3600` · **pending** `15m` · **no data → Normal**

- `summary`: `No rebuild cycle completed for an hour (dev)`
- `description`: `Cycle freshness, not liveness: cycles are event-driven and pause legitimately on quiet nights. If rules 1 and 1a are silent a pod is alive and leads — look at poller_phase errors and at whether the SIRI-SX ingestion timestamp is moving.`

A daytime-attention rule, not an urgent one; consider muting outside 05:00–24:00. No data is
**Normal** here deliberately: rule 1 owns absence, and two rules alerting on one silence is how a
channel becomes unreadable.

**Under the poller lease the gauge is leader-only and dips at a handoff.** Only the leader runs a
cycle, so followers export 0 and the old leader's series vanishes with its pod; between the old
leader's last cycle and the new leader's first, `max()` can read an older value or the followers'
0. The new leader's first cycle is forced (it does not wait for SIRI-SX to move) and runs within a
few minutes of acquiring, inside the 15m pending window, so a handoff does not fire this. The
description's "rules 1 and 1a" wording replaced "rule 1" on 2026-10-13; the live rules carry the old
annotation until an operator updates them (`docs/operations/poller-lease.md`, rollout checklist).

### 2a — Subscription mirror stale · warning

```promql
(max(kix_poller_last_cycle_timestamp_seconds{kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"}) - max(kix_mirror_last_sync_timestamp_seconds{kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"})) and on() (max(kix_mirror_last_sync_timestamp_seconds{kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"}) > 0)
```

**Condition** IS ABOVE `900` · **pending** `15m` · **no data → Normal**

- `summary`: `Rebuild cycles finish but the subscription mirror has not synced for 15 min (dev)`
- `description`: `The webhook pass is matching an old subscription population: a revoked recipient keeps getting alerts and a new one gets none. Look at poller_phase records with phase=notification_mirror and result=error. A sync that keeps truncating at its page budget also grows this: check truncated on the mirror_sync records before treating it as a failure. Past 6 h the store re-seeds itself; past ~24 h revocations are lost for good.`

**Create it only after the deploy that introduces `kix_mirror_last_sync_timestamp_seconds`**, and
only where the webhook channel is on (dev and prd). It replaced `kix_mirror_age_seconds`, which
could not carry this rule. That gauge measured the watermark: the newest document's
`mirror_updated_at`, which says how recently anyone wrote a subscription, not whether the sync
runs. On a quiet collection it grew while every sync succeeded — **21 421 s on a healthy dev pod**
on 2026-09-15 — and the 6 h re-seed bound was measured from it too, so past six hours of quiet
`sync()` re-seeded, `seed()` re-derived the same old stamp, and every later cycle re-seeded again:
a full paged read per cycle (`result="mirror_reseed"` every cycle in `ent-kub-dev`). The bound and
the gauge now both measure the last seed or complete sync, and a sync truncated by its page budget
does not count, because it has not read past its cursor.

**Why the difference from the cycle timestamp rather than `time() - value`.** The sync runs inside
the rebuild, so on a quiet night it pauses with the cycle — `time() - value` would fire whenever
rule 2 would, and two rules on one silence is what this runbook avoids. The difference grows only
while cycles finish and the mirror does not, which is the mirror's own fault: the
`notification_mirror` phase has its own `try/except`, so a failing sync leaves the cycle timestamp
moving. Both `max()`s are for the worker pod, which exports both gauges at `0.0` (the same reason
as rule 1). The `> 0` guard keeps the rule quiet where the mirror never runs — the webhook flag is
off, or the API pod is still before its first seed; a seed that fails from startup is rule 6's,
through the ERROR it logs. 900 s is about five failed cycles at today's 120-185 s period.
One legitimate firing: a backlog drains at most `MIRROR_MAX_PAGES_PER_SYNC` × `MIRROR_PAGE_SIZE`
(20 000) documents per cycle, and a truncated sync does not reset the clock, so a catch-up of
100 000 changed subscriptions runs about five cycles and can cross the threshold while the mirror is
merely behind.

### 2b — Worker stopped · critical

```promql
time() - max(kix_worker_last_tick_timestamp_seconds{kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"})
```

**Condition** IS ABOVE `900` · **pending** `5m` · **no data → Alerting**

- `summary`: `The webhook delivery worker's heartbeat has stopped (dev)`
- `description`: `No delivery round for 15 minutes; the tick moves on every round, including the ones that find nothing. Check the kix-avvik-worker Deployment — scaled to zero, rolled back, or crash-looping. Pending webhook events expire after an hour.`

Rule 1 for the delivery worker, which is its own Deployment (`kix-avvik-worker`) from the same
image. A heartbeat tied to work delivered would page for a worker behaving perfectly, which is why
the tick moves on empty rounds. **Create it only where a worker runs** — dev and prd both do
(verified 2026-09-15); tst renders no workload at all, so there the rule would fire forever.

### 2c — Delivery backlog · warning

```promql
max(kix_delivery_backlog_age_seconds{kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"})
```

**Condition** IS ABOVE `1800` · **pending** `15m` · **no data → Normal**

- `summary`: `Webhook delivery backlog is over 30 minutes old (dev)`
- `description`: `The oldest deliverable pending delivery was minted over 30 min ago, and an event is valid for 60. Response: raise deployment.forceReplicas in helm/kix-avvik/env/worker-values-kub-ent-<env>.yaml — the drain formula is in docs/operations/notification-webhooks.md.`

Deliverable is the operative word and is what keeps this about the QUEUE: rows held by a lease, rows
inside U7's durable backoff and rows past a destination's per-cycle ceiling are all absent from it,
so one unwell receiver cannot drive it — that shows up as `throttled` and `backed_off` on
`webhook_delivery_round` instead. The gauge reads 0 on an empty queue, which is the ordinary state,
and the API pods export 0 for it, which is why the `max()` is there.

### 3 — Pod restarts · warning

```promql
increase(kube_pod_container_status_restarts_total{exported_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"}[15m])
```

**Reduce** Last · **condition** IS ABOVE `3` · **pending** `0m` · **no data → Normal**

- `summary`: `A kix-avvik container is restarting repeatedly (dev)`
- `description`: `More than 3 restarts in 15 minutes. A flapping /health lands here; the crash-loop escape is HEALTH_STALE_AFTER_S=0 through a values-only deploy, which disables the staleness branch.`

Deliberately **not** aggregated: one alert instance per series names the pod and container, and both
Deployments are covered by the namespace selector, which is wanted — hence **Reduce: Last**. Note
`exported_namespace` — `kube_*` comes from kube-state-metrics, whose own `namespace` label is
`prometheus`. The `0m` pending period is also deliberate and is not an oversight beside rule 1's
`5m`: the 15-minute window *is* the averaging, so the rule fires on the first evaluation that sees a
fourth restart, which is when a reader wants to know.

### 4 — Memory near limit · critical

```promql
sum by (pod) (container_memory_working_set_bytes{namespace="kix-avvik", container!="", prometheus_group="kub-ent-dev-001"})
/
sum by (pod) (kube_pod_container_resource_limits{exported_namespace="kix-avvik", resource="memory", prometheus_group="kub-ent-dev-001"})
```

**Condition** IS ABOVE `0.85` · **pending** `5m` · **no data → Normal**

- `summary`: `A kix-avvik pod is near its memory limit (dev)`
- `description`: `Working set above 85 % of the container's limit. Since common 2.x the limit EQUALS the request, so the response is raising memory: in that release's values file. An OOM kill of an API pod at the autoscaler's minimum of one (and always in tst) is a full outage; at two or three it costs that pod's share of traffic, and if it was the leader, a handoff that waits out the 300 s lease TTL.`

The two halves take **different** namespace labels (`namespace` on `container_*` from cAdvisor,
`exported_namespace` on `kube_*`); `sum by (pod)` joins them on the pod name and now spans both
Deployments. Current limits, which the chart derives from the request since common 2.x: **1024 Mi**
for the API in dev and tst, **2048 Mi** in prd, **512 Mi** for the prd worker. (An earlier draft of
this file said ~2457 Mi — that was 1.22.0's limit-above-request arithmetic and has not applied since
the 2.1.0 upgrade.)

### 5 — Pod not ready · critical

```promql
kube_pod_status_ready{exported_namespace="kix-avvik", condition="true", prometheus_group="kub-ent-dev-001"}
```

**Reduce** Last · **condition** IS BELOW `1` · **pending** `3m` · **no data → Normal**

- `summary`: `A kix-avvik pod is not ready (dev)`
- `description`: `At one API pod (the autoscaler's minimum, and always in tst) not-ready means the service is down; at two or three it means one pod is out of rotation. In dev and prd readiness is /ready, which is 503 until the pod's prediction cache and timetable spine have loaded (reason predictions_not_loaded or plan_not_loaded in the body); in tst it is /health, whose dead-or-stale-poller 503s land here. Check the pod's events and logs.`

Per-pod like rule 3, so **Reduce: Last**. Measured 2026-09-15, start to Ready is **29 s in dev and
24 s in prd**, so an ordinary deploy clears the 3m pending period comfortably; a startup that hit
KTD2's documented ~300 s worst case would fire this, which with a single replica is arguably correct
rather than noise. A deploy produces a *second* candidate instance as well as the new pod's: the
outgoing pod's own series goes not-ready before it disappears, which under Recreate (tst, and dev
and prd until their step B) is the normal shape of every deploy and under RollingUpdate is the old
pod's 5 s preStop plus however long its shutdown takes — up to the 270 s grace when it is mid-query,
so a deploy that lands on a slow phase can hold an outgoing pod not-ready past the 3m. That firing
is a deploy artefact while a Ready pod serves beside it; read rule 10 before acting. The 3m pending
period is what covers the ordinary case. Measured on
#219's deploy (2026-09-23): the outgoing pods' series read 1 until they vanished at 08:07:45, the
new ones appeared at 08:08:00, and the new API pod read 0 for about a minute (28 s to Ready, plus
kube-state-metrics' lag). There was no empty minute, and the not-ready minute is well inside 3m.

**No data has been Normal since 2026-09-23. It was Alerting before.** Rules 1 and 2b own absence.
Both Deployments export both heartbeat gauges (the note above), so a missing pod of either
Deployment reads as a stale heartbeat by value, and both pods missing is no data on rules 1 and 2b.
What no-data → Alerting added here was exposure to the query path's own blips. Between 2026-09-18
and 09-23, every rule with no-data → Alerting went `Pending (NoData)` at the same minutes, in both
environments and on `kix_*` and `kube_*` alike: one to four minutes each, 3–11 episodes per rule.
Thanos later returned values for every one of those minutes. Only this rule's 3m pending period was
short enough to fire on one (dev, 2026-09-23 08:17 UTC, with both pods Ready for ten minutes).
Rules 1 and 2b keep no-data → Alerting, because that is what they are for. Their 5m pending period
is the margin against the same blips: about a minute on the longest one seen.

### 6 — ERROR logged · warning

```promql
increase(kix_log_records_total{level="ERROR", kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"}[10m])
```

### 8 — LLM wording failures · warning

```promql
sum(increase(kix_llm_message_total{surface="live", result=~"error|unavailable|truncated|rejected", kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"}[30m]))
/
sum(increase(kix_llm_message_total{surface="live", kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"}[30m]))
and on()
sum(increase(kix_llm_message_total{surface="live", kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"}[30m])) > 5
```

**Condition** IS ABOVE `0.3` · **pending** `10m` · **no data → Normal**

- `summary`: `LLM wording is failing at volume (dev)`
- `description`: `Over 30 % of live wording attempts failed in 30 minutes. Travellers still receive the deterministic template, so this is quality degradation rather than an outage. Check jsonPayload.event="llm_message" for provider and result; VARSEL_LLM_PROVIDER=off is the egress kill switch and VARSEL_LLM_ENABLED=false the bad-text revert.`

**`surface="live"` is load-bearing** — `/meldinger` replay bursts of `ungrounded` are the expected
product of prompt work and must never fire this.

**`error_covered` is excluded on purpose** (2026-10-12). Every rebuild re-words every alerting
train, so most errors were rewrites of a train that already had good text: 319 of prd's 346 errors
from 2026-10-08 to 2026-10-12. A failed rewrite now keeps the previous snapshot's wording
(`varsel._previous_wording`) and is counted as `error_covered`, which the anchored `=~` above does
not match. The rule now fires only when a traveller actually gets the template. Only the poller's
browser path borrows; the webhook and pull paths still count `error`.

**What the first firing taught (dev, 2026-09-19).** Three failures against six attempts in the
thirty minutes to 02:03 — `> 5` is the smallest denominator this rule permits, and at dev's night
volume six attempts is what a busy half-hour looks like. All three were `504 DEADLINE_EXCEEDED`
from Vertex, which is **our own deadline, not Gemini being down**: google-genai turns
`http_options.timeout` into an `X-Server-Timeout` header, so Vertex refuses at the 8 s
`llm_message._TIMEOUT_S` (the two `499 CANCELLED` seen the same day sit inside 504 clusters, which is
consistent with being the client half of one). Raising that timeout was considered and refused —
mean call 2.1 s (dev) / 2.2 s (prd), p99 5.0 s, and not one of the 1 776 Gemini calls those two
projects completed over 24 h took longer than 6.3 s, so the cut sits 1.6× above p99. That count is
every `gemini-3.7-flash` invocation in the project, `AI.CLASSIFY` included, not the wording path
alone. Note Vertex's own `model_invocation_latencies` counts the `200`s **only**: the
timed-out requests are in `model_invocation_count{response_code="504"}` and in no latency
distribution at all, which is why the wording record now carries its own `ms`.

**The second firing corrected the diagnosis, and the fix is a retry rather than a longer deadline
(dev, 2026-09-20).** `query=0.333` at 00:12, Slack 00:17: seven failures in the 30 minutes to
00:04:45, six of them in one burst. Do not try to reconcile the denominator against the log — the
entries hold **14** attempts in that half hour (7 errors, 7 ok), a true ratio of 0.5, while Grafana
read ~21 because `increase()` extrapolates a counter to the range boundaries. Every one was `504 DEADLINE_EXCEEDED`
again, but this time the records carried the `ms` the firing above was instrumented for, and it
says the **opposite** of what was concluded then: they returned at **5.27-5.29 s**, not at the 8 s
header, while five successes in the same batch took 1.3-2.8 s. So Vertex gave up on its own, our
deadline was never reached, and the two `499 CANCELLED` reading as the client half of one is a
claim that only ever held for a 504 at ~8 s. prd 504'd in the same SECOND (00:04:45.77), which is
what puts the cause upstream rather than in either cluster; prd was still on the pre-`ms` build, so
it can say nothing about duration.

What changed in response: `llm_message._RETRY_OPTIONS` gives the google-genai client **two**
retries (it had none — `retry_args(None)` is the SDK's `stop_after_attempt(1)`, so the tenacity
frames in the traceback were a wrapper doing a single attempt). A stateless API at this scale will
very likely land a later attempt on another server, and a retry is invisible to this rule: a
recovered call increments `result="ok"` alone.

The per-attempt deadline came **down** with it, 8 s → 6 s, and the two are one decision. `timeout`
is per attempt, so three attempts at 8 s is a 26 s worst case inside a 30 s pass — a pass that
admits almost nothing after its first call. At 6 s the worst case is 20 s (3 × 6 + 2 × 1), which is
the most `varsel`'s write pass can reserve and still have its CALL cap bind before the clock (16
workers at ~2.2 s fit ~72 calls into the 10 s that leaves, against a cap of 64). The clipping that
buys is small and no longer expensive: of dev's 81 successful calls in the 24 h to that morning 18
took over 3 s, 4 over 4.5 s and none over 6 s, and across both projects' 1 776 Gemini calls that
day p99 was 5.0 s and the slowest 6.3 s — so ~1 call in 1 000 is cut short, and that call now gets
two more attempts instead of falling through to the template. `/meldinger`'s replay pass pays the
same reservation: ~40 → ~18 calls per request, a full page in ~11 «Hent flere» rounds rather than
~5, with `MELDINGER_REQUEST_DEADLINE_S` as the lever if that becomes tiresome.

Two things to watch after the deploy. An `ok` record with `ms >= 7000` is a retry that saved a
wording — that is the evidence this worked. Failures still arriving at `ms ≈ 20 000` mean the blip
outlasts both 1 s waits and attempts are not the lever; `initial_delay` is, and it has to come out
of the same 20 s. Expect one unstructured INFO line per retry from tenacity's `before_sleep_log` on
the `google.genai` logger — three attempts means up to two per failed call.

**The third firing corrected the diagnosis again, and this time the correction is the opposite of
the second one (prd, 2026-09-21).** `query=0.4286` at 10:51 Oslo — prd's first firing of this rule.
Three `504 DEADLINE_EXCEEDED` in two bursts (08:35:11.50, 08:35:11.99, 08:39:08.77 UTC) against
nine real attempts in the window, a true ratio of 0.33; Grafana's 3/7 is `increase()` extrapolation
as above, again not worth reconciling. Travellers on the affected trains got the deterministic
template. **prd could say nothing about duration because prd was eight days behind main** — the
last `workflow_dispatch` promotion was 2026-09-13, so prd carried neither `ms` (#207) nor the retry
(#209), and every record in that window has `ms` absent. Read that first when prd and dev disagree
about a wording problem: `gh run list --workflow=cd.yml` and look for the last dispatch, because
pushes only reach dev.

**What dev's own data says, and it overturns the paragraph above.** Dev ran the same upstream blip
through the 6 s header WITH the retry, and its `ms` values reveal that `X-Server-Timeout` is
enforced server-side with Vertex answering ~2.6 s before it expires. Single-attempt calls, dev:

| header | successes | slowest success | fastest 504 | successes in 3.6–5.0 s |
|---|---|---|---|---|
| 8 s (09-19 11:30 → 09-20 11:36 UTC) | 77 | **4998 ms** | **5137 ms** | 10 |
| 6 s (since 09-20 11:36 UTC) | 121 | **3516 ms** | — | **0** |

The boundary is sharp in both eras — not one success above it, not one failure below it — and it
moves 1.5 s when the header moves 2 s. So the second firing's conclusion that "Vertex gave up on
its own, our deadline was never reached" is **wrong**: the 5.27–5.29 s 504s were the 8 s header
minus Vertex's own overhead, and the first firing's reading was right after all. The consequence is
that #209's deadline half cut the model's time from ~5.4 s to ~3.4 s — its own comment claimed
"6 s clips roughly one call in a thousand", derived by treating the header as the cut, while the
same file's distribution had 18 of 81 calls over 3 s. Measured after the fact it moved ~13 % of
first attempts onto the retry path, where a failure now costs three attempts and ~11–12 s instead
of returning in ~4 s.

The retry half works and is keeping the numbers respectable: dev on 2026-09-21 returned `ok` at
5600, 6047 and 9813 ms after one or two 504s — three wordings a traveller received instead of the
template — and dev's error rate over the post-deploy day is 6.5 % against 9.4 % over the 8 s day.
But the failures are payload-correlated rather than a server lottery: of the seven first-attempt
504s that day, five also failed the second attempt and four the third. A wording that needs 4.5 s
needs it every time, so retries rescue only the boundary, and the lever is the per-attempt deadline.

**The fix re-splits the same 20 s** (`llm_message`, 2026-09-21): `_TIMEOUT_S` 6.0 → **9.5** and
`attempts` 3 → **2**, so `_WORST_CASE_CALL_S` is 20.0 exactly as before and no caller's reservation
moves — `varsel`'s and `meldinger`'s pins hold untouched. Model time goes ~3.4 s → **~7.4 s**, wider
than the 8 s header ever gave, with one retry kept for the genuine transient (the six simultaneous
504s of 2026-09-19, and dev and prd failing in the same second). Note even those crossed our own
cut, which is the general shape of this failure: **a tight header converts upstream latency variance
into lost wordings.**

Two details a later reader needs. The header is `ceil(_TIMEOUT_S)`, so 9.5 s sends
`X-Server-Timeout: 10` and the server cut is ~7.4 s, not 6.9 — irrelevant while the value was 8.0
or 6.0, and 9.5 is the first non-integer one. What bounds the reservation is the separate
CLIENT-side httpx deadline at 9.5 s, which aborts first, and that is why a fractional value is safe
here: Vertex is given a whole second more than we will wait for it. And **both failure mechanisms
stay open** — the tight cut is what makes singleton calls fail, but in the 8 s era 7 of 8 failures
sat inside bursts (six in one second at 22:04:45, one in a burst of five at 11:52), so concurrent
slowness crossing the cut is the other half and has not been ruled out. `_VERTEX_HEADER_OVERHEAD_S` now names the gap so the effective cut is
derivable, and `test_llm_message` fails if a future change puts it back inside the measured success
distribution. Re-measure that constant the same way after an SDK or endpoint change; it cannot be
read off Vertex's `model_invocation_latencies`, which counts the 200s only.

**What confirms or refutes this after the dev deploy**, from `jsonPayload.event="llm_message"` and
the `google_genai._api_client` retry lines that delimit attempts:

- Single-attempt `ok` records reappear **in the 3.6–7.3 s band**, which is empty under the 6 s
  header. Their count is how many wordings the re-split buys back.
- Any remaining 504 attempt returns at **~7.3–7.4 s**. This is the falsifiable half: a 504 at 3.3 s
  or 5.3 s means the header-minus-overhead model is wrong and `_VERTEX_HEADER_OVERHEAD_S` is not
  what it claims.
- The SHAPE says which mechanism is left. Burst-shaped 504s at ~7.4 s are shared upstream slowness
  and the retry is doing its job; SINGLETON 504s at ~7.4 s are payloads that genuinely need more
  than 7 s, and how many there are is what decides whether the 20 s wants re-splitting again.

**Measured an hour after the deploy: confirmed, and the one surprise is a different failure class**
(dev, 2026-09-21, 23 wording calls in the 58 minutes from 11:55 to 12:53 UTC, all on the new pod
`kix-avvik-67d6f88665-75kqn`, which logged startup complete at 11:54:12 — the old pod was still
writing records at 11:53:40, so a window starting any earlier mixes the two builds).

**The fix works.** Zero `result="error"` records, against 9.4 % over the 8 s day and 6.5 % over the
6 s one. Four calls failed their first attempt and **all four recovered on the second**, where the
6 s build's own records that same morning show four of seven exhausting all three attempts. Read
the 0 % as consistent-with rather than proof — at ~2 calls per ~296 s cycle, 23 calls expects 1–4
failures, so the rate alone is thin. What is not thin is 4 of 4 rescued.

**(a) Confirmed.** Warm single-attempt successes are back in the band: **2 of 12, at 5801 and
6577 ms**, against ~13 % predicted, in a 3.6–7.3 s band that held **0 of 121** under the 6 s header.
The retried singleton's second attempt also succeeded in 6.07 s. Two cautions. The first concurrent
wave after startup (8 calls, 11:55:12–17, one reading **9106 ms** on a single attempt) is
**cold-start contaminated and excluded**: `started = monotonic()` is taken before `_call_backend`,
which builds and caches the client, so that wave's `ms` carries ADC resolution and a
metadata-server token rather than model time. And n=12 cannot separate 17 % from 13 %.

**(b) Confirmed, once the failures are read by class.** Both 504s returned late, as predicted:
the clean singleton at 11:57:30 at **7.17 s** (then `ok` in 6.07 s, ms 14239) and one inside the
burst at **6.78–7.17 s** (pairing-ambiguous, three concurrent calls against three retry lines).
Implied overhead **2.83 s** on the clean one, against the 2.6 the constant carried — so
`_VERTEX_HEADER_OVERHEAD_S` is now **2.9**, the conservative end of the range the three headers
imply (8 s → 2.71–2.87 over 8 records, 6 s → 2.40–3.00, 10 s → 2.83–3.22). **No 504 arrived early.**

The two fast failures at ~3.6–4.1 s, which the criterion above would have read as a refutation,
are **`429 RESOURCE_EXHAUSTED`, not 504s at all** — the four retry lines carry two distinct bodies
and that is the whole discriminator. A quota rejection returns fast because no model work is
attempted, so it has no relationship to the header, and the criterion should have said *504* rather
than *any failure*. Two things follow. The ceiling claim is now confirmed at three headers —
slowest single-attempt success **4998 ms at 8 s → 3516 ms at 6 s → 6577 ms warm at 10 s** — and
`_VERTEX_HEADER_OVERHEAD_S` should still be read as "how far below the header success becomes
impossible", never as "when a failure arrives", because a 429 arrives whenever quota says so. And
**the retry now rescues quota rejections too**, which #209 never claimed: both 429s landed inside
the one concurrent burst and both succeeded on the second attempt. That is the shared-project
Vertex quota this repo already warns about under `/meldinger`, and it is worth watching separately
— it scales with burst WIDTH (`_LLM_WORKERS`), not with the deadline.

**(c) Both shapes present, neither yet a reason to act.** One 3-call burst (two 429s and one 504,
all rescued) and one singleton whose retry succeeded in 6.07 s — so not a payload inherently
needing more than 7 s, just a transient. No sign yet of the singleton-504-at-7.4 s class that would
argue for re-splitting the 20 s again; that stays the thing to watch.

**prd needs the promotion, in this order**: land the re-split, confirm the above in dev, then
`gh workflow run cd.yml -f environment=prd` — which also puts `ms` in prd, so its next firing is
diagnosable from prd's own records instead of by inference from dev. Promoting main as it stood
would have exported the 3.4 s cut to the environment with real travellers on it.

**The other half of the noise fix is this rule's own shape, and it is not done.** `> 5` is a floor
on ATTEMPTS, not on failures, so at dev's ~2 calls per cycle a single six-failure burst reaches
0.33 on a denominator of 21 and always will. A `failures >= N` floor beside the ratio is what would
make this rule mean "at volume" in dev as well as in prd; left as an open question because the
retry shrinks the numerator first and the next firing is the evidence for whether more is needed.

**It resolved on the GUARD, not on the errors ageing out** — `Normal (nodata)` at 02:19:40, and
the mechanism is worth knowing because the obvious expectation is wrong. The window did not become
healthy; it became too small to judge. At 02:18:35 the first of the three successes fell out of the
30-minute window, the total dropped to five, `> 5` stopped matching, and the expression returned
nothing at all. Empty is what `no data → Normal` reads as healthy, and here that is the correct
reading: fewer than six attempts is not evidence of anything. Expect every firing of rules 7 and 8
to end this way on a quiet environment rather than by the ratio falling. The Slack side lags the state
change: FIRING at 02:12:40 arrived 02:13, `Normal` at 02:19:40 arrived **02:23**. That is the
delivery-side grouping, not the rule — do not read a missing all-clear in the first few minutes as
the alert still standing. It does send one, which is worth knowing: a contact point that delivers
firing and never resolved leaves every incident looking open.

**The repair is verified in production, by one sample.** Rule 8 was re-saved at 17:35:50 on
2026-09-18 with the outer parentheses; the entry that proves they took is `Normal (nodata)` at
22:56:40, where the 30-minute window held **eight attempts and two errors** — past the `> 5` guard,
at a ratio of 0.25, under the 0.3 threshold. The unparenthesised form returns the ratio unfiltered,
so it would have sat there at `query=0.25` heading for Alerting; instead the expression filtered and
the rule went quiet. A firing above the threshold proves nothing about the brackets — both forms
fire there. **Only a sample that clears the volume guard and stays UNDER the threshold does**, which
is why this one is recorded rather than the two firings either side of it.

**Read `ms`, `journey_digest` and `situation_number` on the record before reaching for a switch.**
Every `event="llm_message"` record carries all three since 2026-09-19, on failures as well as on
`ok`. `ms` says whether a longer deadline would have helped; the digest and the situation say
whether one subject is failing across cycles, which is what separates a stall from a payload the
model will refuse every time. A transient failure is already retried on the next cycle against
`_MAX_TRANSIENT_ATTEMPTS` (12) — what it costs is that the push that went out carried the template,
since `_notified` means the train reaches a phone once.

### 9 — Labelling stale · critical

```promql
(time() - max(kix_labelling_last_success_timestamp_seconds{kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"}))
and on()
(sum(increase(kix_decision_write_total{result="ok", kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"}[48h])) > 0)
```

**Condition** IS ABOVE `172800` · **pending** `30m` · **no data → Normal**

- `summary`: `Outcome labelling has stopped (dev)`
- `description`: `48 hours without successful labelling while decisions were still being written. Unlabelled decisions become permanently unknown after 10 days. Check the varsel-label-daily scheduled query in this environment's project.`

**`and on()`, not `and`** — see the third note at the top of this section; with a bare `and` this
rule can never fire. The work gate is the metric-side echo of the in-app labelling-freshness
detector's own gate, and the two windows differ slightly (here: decisions written in 48 h; in-app:
decisions whose `call_date` is 2–10 days old), which is fine for a belt-and-braces rule beside rule
6's primary. No data is **Normal** deliberately: the gauge is 0 until something has been labelled at
all, which is the normal state of a fresh deployment, and the work gate is what keeps that quiet.

**This rule cannot be verified from its own history, and rules 7 and 8 can.** Their defect is loud
or latent — a Pending whose `query` value sits BELOW the threshold is the signature, and one turns
up as soon as the environment clears the volume guard at a healthy ratio. This rule has no such
signature in either direction. Folded, a HEALTHY rule 9 returns nothing, because the comparison
filters a normal freshness figure; the broken `(writes > 0) > 172800` form returns nothing either.
Both read `Normal`, with no data, indefinitely, and no amount of waiting tells them apart. Nor does
lowering the threshold in Explore: at `> 0` the broken form's guard passes too and both return a
value. **The only check is textual** — the expression must OPEN with `((time()` and the bracket
closing the guard must come BEFORE the final `> 172800`. Pasting the correct string over it is
idempotent, so when in doubt, paste. This is the rule the thesis at the top of this document is
about: it has never fired, it never will if it is wrong, and `Normal` is what both states look
like.

### 11 — p99 latency · warning

```promql
histogram_quantile(0.99, sum by (le) (rate(kix_http_request_duration_seconds_bucket{path!="health", long_poll!="true", kubernetes_namespace="kix-avvik", prometheus_group="kub-ent-dev-001"}[5m])))
```

**Condition** IS ABOVE `5` · **pending** `10m` · **no data → Normal**

- `summary`: `p99 request latency is above 5 s (dev)`
- `description`: `Golden-path default threshold, not yet tuned against this app's real traffic. Check whether one path dominates before treating it as a regression.`

**`long_poll!="true"` since 2026-09-25.** The rule's first firing (dev, 15:55 Oslo, `query=10`)
was a caller of `GET /notification-api/v1/journey-alerts` polling five journeys every ~2 min with
`wait=10` during an L1 disruption: every read was a figures miss that waited on fresh Gemini
wordings, so each one took the 10 s it had asked for, and at dev's volume four such reads per
window are more than 1 % of requests. `10` is not a measurement either -- the histogram's top
finite bucket is 10 s, so any p99 above it reads as exactly 10. The handler now marks a read whose
`wait` is above 0 (**including a read with no `wait`, which defaults to 20 s**) and the middleware
files its duration under `long_poll="true"`; `wait=0` reads stay in the rule, so a journey-alerts
read that is slow without being asked to wait still counts. Edit the Grafana rule in both
environments when this reaches them -- before that deploy the label does not exist and
`long_poll!="true"` matches every series, so the edit is safe in either order.

## How the rules were actually created (2026-09-18)

Twenty-six rules exist: thirteen per environment. In dev, rule 1 was built by hand and the other
twelve were imported; in prd all thirteen were imported. The route is written down here because the
import dialog reshapes a rule in ways that are not obvious and that this file's own tables cannot
express.

**grafana.entur.org's importer takes Prometheus-format YAML only.** It does not read Grafana's own
provisioning JSON — the format `Export` produces — so the export is useful as a SCHEMA REFERENCE
and not as a carrier. The practical route is: build one rule by hand, export it to learn the exact
shape this Grafana speaks (data source UID, the `reducer` that sits inside the threshold condition,
`OK` as the wire spelling of no-data "Normal"), generate the rest from this file in that shape, then
convert to Prometheus YAML for the dialog. The **provisioning API** carries everything, and it
turned out to need no token. Called from a logged-in grafana.entur.org page, it accepts the session:
verified 2026-09-23 by reading and updating these rules, and the repairs below went through it. Send
`X-Disable-Provenance: true` on every write. Without it, Grafana marks the rule as API-provisioned
and the UI no longer lets anyone edit it. Until then this file said the route needed a
service-account token from an org admin; nobody had tried the session.

**Three things the format drops, all of which have to be set by hand afterwards.** *Pause imported
alerting rules* defaults ON, so an unattended import yields rules that look perfect and are silent.
*The contact point* has no Prometheus equivalent, so every imported rule lands on **Use notification
policy** — the shared tree whose fall-through is `entur-pagerduty` with nobody behind it — and needs
`alerts-kix` selected per rule. *The no-data setting* takes the importer's default, and so does
*the error setting*, which comes out **Normal**, against the ground rules' **Error**.

**Folding a threshold into a Prometheus expression must be parenthesised, and getting it wrong is
not symmetric.** Prometheus format has no separate condition node, so the comparison goes inside the
expression — and PromQL binds comparison tighter than `and`, so appending it to a rule that ends in
an `and on()` guard attaches it to the GUARD:

```promql
ratio and on() guard > 5 > 0.3      # parses as: ratio and on() ((guard > 5) > 0.3)
(ratio and on() (guard > 5)) > 0.3  # what was meant
```

The first form returns the ratio unfiltered, and a Prometheus-format rule fires on any returned
sample, so it alerts on a healthy value. Measured on the day: rule 8 went Pending with **0 errors
against 32 successes**, rule 7 carried the same defect and read Normal only because dev had no
pushes in the window, and rule 9's version — `(writes > 0) > 172800` — was false unless dev wrote
172 800 rows in 48 h, so it could **never fire** and read Normal forever. One loud, one latent, one
vacuous, from one missing pair of brackets.

**A folded expression cannot tell "healthy" from "the series is gone", and three rules depend on
that distinction.** When the comparison is inside the query, a healthy rule returns nothing — the
same empty result an absent series gives. So for rules **1, 2b and 5**, whose no-data must ALERT
because a dead pod, a scrape failure or a worker scaled to zero is exactly what they are for, the
query must return a VALUE and a threshold node must do the comparing (the shape `Export` shows:
query `A`, threshold `C`, `reducer: last` inside `C`). Those three are hand-built for that reason.
The other ten are correct folded, with no-data **Normal**: their empty result IS the healthy state.
In dev that meant one hand-built rule and two conversions after the import; in prd, three
conversions, since nothing there was hand-built.

**None of those five conversions took, and the five rules read Normal for five days because they
could not fire** (found 2026-09-23). The importer does not produce the query-plus-threshold shape.
It produces three nodes:
- `query`, the expression;
- `prometheus_math`, which is `is_number($query) || is_nan($query) || is_inf($query)`. It returns
  **1 for every series the query returns, whatever the value.** A Prometheus-format rule fires on
  any sample it returns, NaN included, and this node is how Grafana expresses that;
- `threshold`, which reads `prometheus_math` and compares it with `> 0`.

The conversions changed the threshold's comparison to `< 1` and `> 900` but left its input on
`prometheus_math`. Each threshold therefore compared a constant 1, and the rule could fire only on
no data. The affected rules were 2b and 5 in dev and 1, 2b and 5 in prd; only dev's hand-built
rule 1 had the right shape. Every check this file asked for passed: the query returned a value in
Explore, and the rule read Normal. The fault surfaced only when rule 5 fired on a query-path blip
while both pods were Ready (see rule 5's section). The repair was applied to all five that day:
**delete `prometheus_math` and set the threshold's input to `query`**, the shape Export shows for
the hand-built rule. Rule 5 no longer needs the value shape, since its no-data is now Normal, but it
keeps it, and that shape is correct either way.

**Prove that a rule can fire, not just that its query returns a value.** Grafana's rule test
evaluates every node: use the editor's **Preview**, or `POST /api/v1/eval` with the rule's `data`
and `condition` from a logged-in page. That is the call Preview makes, and it saves nothing. Force
the query into the failing range, and the condition node must return **1**; unmodified, it must
return **0**. For rules 1 and 2b, append `+ 100000` to the query; for rule 5, `* 0`. For a folded
rule, lower the comparison inside the expression until healthy data crosses it, as rule 8's section
did by hand. Measured 2026-09-23: all five blind rules returned 0 when forced, and 1 after the
repair. One case was live: #220's API pod was mid-startup at `query=0`, and blind rule 5 read it as
Normal.

**Import the second environment under a different GROUP NAME.** Both files were generated as group
`kix-1m`, and the prd import would have landed on the group the thirteen repaired dev rules already
occupied in the same folder — whether this Grafana would have merged, refused or REPLACED was not
worth finding out with the dev rules underneath. prd was imported as `kix-1m-prd`. A group is an
evaluation bucket and nothing else keys on its name, so the rename costs nothing; read the confirm
dialog for a title belonging to the other environment before clicking through either way.

**The `kix_.*` arrival check in step 1 says nothing about rules 4, 5 and the restart rule.** Those
select `kube_*` and `container_*`, each family with its own namespace label (ground rules), and a
wrong label returns nothing — which under the folded shape is indistinguishable from healthy, the
same silence that hid two of the three bracket defects above. Paste those three inner expressions
into Explore against the environment's own `prometheus_group` before calling it done.
