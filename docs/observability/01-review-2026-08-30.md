# Observability review — what we have, what Entur recommends, what to fix before ramping traffic

**Date:** 2026-08-30
**Scope:** the `/disruptions` API deployment on GKE (dev/tst/prd), its poller, the four
front-ends, and the BigQuery scheduled jobs. Compared against Entur's golden-path guidance
(`entur/ai` → `guides/reference/{logging,observability,alerting,tracing}.md`,
`guides/platform/common-helm.md`), with the current state measured in prd Cloud Logging and
Cloud Monitoring on 2026-08-30.

> **Status 2026-10-13 — this review is a historical baseline; §1's "none" no longer holds.** It was
> worked through by `docs/plans/2026-09-11-001-feat-observability-hardening-plan.md`, and the
> operator half lives in `02-alert-rules-2026-09-11.md`. Done: R1 (poller heartbeat in `/health`,
> `thread_died` excepthook), R2 (`metrics.py`, scraped on port 9464), R3 (Grafana rules in dev and
> prd, routed to Slack `#alerts-kix` — PagerDuty was declined), R4 (`labelling_stale` plus rule 9),
> R5 (`/health` access-log filter, `LOG_LEVEL`, warn-once baselines, structured push failures,
> `test_logging_setup.py`), R6 (`smoke-*` jobs in `cd.yml`) and R7 (`terraform/monitoring.tf`).
> OpenTelemetry tracing was built after all, against §4's proposed deviation (on in dev and prd).
> Still open: readiness is the same probe as liveness, there is no request-ID middleware (trace
> correlation on log lines covers most of it), the internal front-ends have no client-error
> reporting, most alert rules have never fired outside a forced test (02, checklist step 8), and rule 2a
> (subscription mirror stale) still has to be created in Grafana once its metric is deployed.

**Headline:** logging is in good shape — structured JSON with correct severity mapping and a
rich `event=` vocabulary that already answers most "what happened?" questions. Everything
*downstream* of logging is missing: no metrics, no alerts, no uptime check, no post-deploy
verification, and no detector for the two failure modes that matter most — a silently dead
poller thread and a silently failing nightly labelling query. Today, every failure mode of
this system is detected by a human reading logs or a traveller not getting a push.

## 1. What we have today

### 1.1 Logging — the strong half

One central config, `disruptions/api/logging_setup.py` (called at import time from `main.py:23`):

- **Structured JSON to stdout**, one object per line: `timestamp` (ISO-8601 UTC), `severity`,
  `message`, `logger`, plus arbitrary flat fields via `extra={"fields": {...}}`. This meets the
  golden path's required-field list exactly, and Cloud Logging parses it: verified in prd that
  entries land as `jsonPayload` with the LogEntry severity promoted correctly (WARNING lands as
  WARNING).
- **Uvicorn's handlers are stripped and re-routed** through the same JSON handler, so access
  logs and startup logs are structured too — including the stderr error log that would
  otherwise arrive unparsed.
- **~30 structured `event=` names** (catalogue in Appendix A) covering the poller
  (`poller_cycle`, `poller_phase` with per-step `ms`), the push audit trail (`push` with
  device, journey, probabilities), LLM calls (`llm_message` with provider/result), togvarsel
  rounds, decision-log writes, alternatives lookups, and client errors. Several past incidents
  were diagnosed from exactly these events; the raw material for log-based monitoring is
  genuinely good.
- **Client-side error reporting** exists for the `/varsel` PWA (`POST /varsel-api/client-log`
  → `event="client_error"` at WARNING, rate-capped at 60/min). The other three front-ends
  (`/demo`, `/historikk`, `/meldinger`) have none.
- Logs for the GKE workload live in **`ent-kub-prd`** (the cluster host project), not
  `ent-kixavvik-prd` — the standard platform split. Anyone building saved queries needs to
  point at the right project.

Known blemishes (details in §3):

- Root level is hard-coded `INFO` with no `LOG_LEVEL` override (`logging_setup.py:56`). The one
  DEBUG record in the codebase — the `llm_message_prompt` prompt/reply dump behind
  `VARSEL_LLM_LOG_PROMPTS` (`llm_message.py:1188`) — is therefore **filtered out even in dev,
  where the flag is set**. The switch has never emitted anything.
- `/health` probe hits are access-logged at INFO every few seconds (~2 probes × every 5 s,
  verified in prd) — pure noise and Cloud Logging ingestion cost.
- prd logs `event="reisevalg_baselines_unavailable"` at WARNING every ~5–7 minutes, forever:
  `svv_baselines` is *deliberately* absent in prd (see CLAUDE.md, Reisevalg section). A
  permanent, expected condition occupying the WARNING channel trains readers to ignore it.
- Web-push **failures** log their detail (status, host, body) as unstructured prose
  (`varsel.py:1589-1596`) beside the structured `event="push"` audit event — the failure half
  of the audit trail is harder to query than the success half.
- `logging_setup.py` — the single point of failure for every log line's format — has no test.

### 1.2 Health checks

- `GET /health` (`main.py:2527`) returns a static `{"status": "ok"}` and checks **nothing**.
- Both liveness and readiness probes point at it (`helm/kix-avvik/values.yaml:15-19`), so
  readiness carries no information liveness doesn't. The chart's default tcpSocket startup
  probe (300 × 1 s) covers the slow lifespan start — that part is deliberate and fine.
- **Consequence:** the poller is a `daemon=True` thread (`main.py:1124-1130`). If it dies, the
  pod stays Ready and Live indefinitely while serving stale predictions and sending no pushes.
  Nothing restarts it, nothing alerts, and the only trace would be an *unstructured* stderr
  traceback (Python's default `threading.excepthook` bypasses the logging module) plus the
  *absence* of `poller_cycle` events — and since `poller_cycle` only fires when upstream
  SIRI-SX moves, a dead poller and a quiet Saturday night look identical in the logs.

### 1.3 Metrics, alerting, tracing, dashboards — none

- No `/metrics` route, no `prometheus_client` (or any metrics/tracing/APM library) in any
  requirements file, and `common.container.prometheus` is never set in Helm, so no scrape
  annotations are rendered.
- No Grafana alert rules, no `google_monitoring_*` or `google_logging_metric` resources in
  Terraform (`terraform/` holds only the BigQuery dataset IAM), no uptime check on
  `kix-avvik.entur.io`, no dashboards.
- No OpenTelemetry, no trace/span/request-ID correlation on log lines.
- What *does* exist without any work from us: GKE system metrics (`kubernetes_io:*` in Cloud
  Monitoring, `kube_*`/`container_*` in the shared Prometheus/Thanos behind
  grafana.entur.org). Verified: `kubernetes_io:container_restart_count{namespace_name="kix-avvik"}`
  answers in `ent-kub-prd` (0 restarts in the last 24 h). Pod-level alerting is therefore
  possible **today, with zero code changes** — nobody has created the rules.

### 1.4 CI/CD and scheduled jobs

- `cd.yml` hands off to `entur/gha-helm` and ends. **No post-deploy verification** — no health
  curl, no smoke test, no check that the served bundle matches the build (the exact blind spot
  behind the 2026-08-13 "deploy looked absent" incident, which the `_VersionedStaticFiles` fix
  mitigates but nothing verifies).
- The BigQuery scheduled queries (`varsel-label-daily` in dev+prd, `demo-recent-daily`,
  `demo-copy-daily`) have **no failure notification of any kind** — no
  `notification_pubsub_topic`, no email preference. The repo itself documents two silent
  failure modes (transfer config holds a *copy* of the SQL; an outcomes-table schema change
  breaks the INSERT "every night until someone notices") and a hard deadline: rows not
  labelled within the 10-day retry window are **unknown forever**. Detection today is a manual
  `bq ls --transfer_run`.

## 2. What Entur recommends (golden path)

From `entur/ai` — the platform's requirement words (MUST/ALWAYS vs SHOULD) preserved:

| Area | Recommendation | kix-avvik today |
|---|---|---|
| Logging | Structured JSON to stdout; `timestamp`/`severity`/`message` required; never log PII/secrets; Python: std `logging` + JSON formatter | ✅ Compliant (custom formatter, equivalent) |
| Log correlation | `traceId`/`spanId`/`requestId` recommended on request-scoped lines | ❌ None |
| Liveness probe | MUST exist; ALWAYS verify only the process itself | ⚠️ Exists but static; can't see a dead poller |
| Readiness probe | MUST exist; ALWAYS check only private resources | ⚠️ Same endpoint as liveness, checks nothing |
| Metrics | All services must expose Prometheus metrics; Python via `prometheus_client`; enable `common.container.prometheus` in Helm | ❌ None |
| Alerting | Grafana rules (grafana.entur.org, Thanos data source) in a team folder, routed to PagerDuty via the `entur-pagerduty` contact point with `service_name`/`env`/`severity` labels. Alert on symptoms, not causes | ❌ None |
| Minimum prd alert set | 5xx rate > 5 % (5 m, critical) · p99 > 5 s (10 m, warning) · > 3 restarts/15 m (warning) · memory > 85 % of limit (5 m, critical) · readiness failing (3 m, critical) | ❌ None exist |
| Tracing | OTel → `telemetry.googleapis.com`, traces land in `ent-kixavvik-<env>`; sampling 0.1–1 % in prd | ❌ None (see §4 — proposed deviation) |
| Deploy-to-prd checklist | "Confirm observability is wired" is an explicit checklist item | ❌ Not done |

GCP Cloud Monitoring alerting is documented as *supported but not the recommended path* —
Grafana is the single pane of glass. One consequence for us: **Grafana alerts evaluate
Prometheus metrics, not logs**, so our rich log events can't drive golden-path alerts until
the app exports metrics (or we accept the non-preferred Cloud Monitoring log-based-metric
route).

## 3. Gaps ranked by what they cost during a traffic ramp

1. **A dead or wedged poller is invisible** (§1.2). This is the single worst gap: the entire
   product (predictions, pushes, togvarsel rounds) hangs off one daemon thread in one pod, and
   its failure mode is *silence*. At pilot scale a colleague notices eventually; at 10× the
   users notice first.
2. **No alerting at all** — even the zero-code pod-level alerts (restarts, memory vs the
   2457 Mi prd limit, readiness) don't exist. Memory is the concrete one: one always-on
   process with in-process caches that grow with registrations, and an OOM kill would today be
   discovered by reading logs.
3. **Silent scheduled-query failure** destroys the feedback loop (`/historikk` verdicts) with a
   10-day point of no return — and it has already broken twice for documented reasons.
4. **No post-deploy verification** — the one incident class we've measured (stale `index.html`
   masquerading as a failed deploy, 2026-08-13) cost about an hour of CI/Helm archaeology and
   would again.
5. **Log hygiene** — chronic WARNING in prd, probe spam at INFO, unstructured push-failure
   detail, dead DEBUG switch. Cheap to fix, and the WARNING channel needs to be trustworthy
   *before* alerting is built on top of the log stream.
6. **No request-rate/latency/5xx visibility** on a public, unauthenticated API. The abuse
   ceilings inside the app (`/meldinger` budgets, client-log caps) are enforced but not
   observable; the golden-path 5xx/latency alerts have no metric to evaluate.

## 4. Recommendations

### P0 — before ramping traffic

**R1 — Poller heartbeat, visible three ways.** (small code change, highest value)
- In `poll_for_changes`, record a module-level `last_tick_at` (UTC) once per loop iteration,
  unconditionally — a *tick* heartbeat, independent of whether SIRI-SX moved, so it has no
  upstream dependency and is safe in a probe.
- Make `/health` fail (503) when the poller thread is not alive or `last_tick_at` is older
  than a generous multiple of the poll interval (e.g. 10 min). This stays inside the golden
  path's "process only" rule: a dead poller thread *is* a broken process, and a pod restart is
  the correct and complete remedy — this single change makes the failure self-healing.
  Keep BigQuery and all upstream checks out of the probe.
- Install a `threading.excepthook` that routes thread deaths through the JSON formatter as a
  structured ERROR (`event="thread_died"`), so the traceback is queryable instead of a raw
  stderr `textPayload`.

**R2 — Prometheus metrics endpoint + scraping.** (a day of work; unlocks everything in R3)
- Add `prometheus_client`, mount `/metrics`, set `common.container.prometheus.enabled: true`,
  `path: /metrics` in `values.yaml`.
- First metric set, mostly mirroring what the logs already record so nothing new is invented:
  - `kix_poller_last_tick_timestamp_seconds` and `kix_poller_last_cycle_timestamp_seconds`
    (gauges) — staleness alerts come from `time() - gauge`.
  - `kix_poller_phase_duration_seconds{phase}` (histogram or gauge) — the `_phase`
    instrumentation exported instead of only logged.
  - `kix_push_total{kind,result}` — mirrors `event="push"` (`sent`/`gone`/`error`).
  - `kix_llm_message_total{provider,result}` — mirrors `event="llm_message"`.
  - `kix_decision_write_total{result}` — mirrors `event="varsel_decision_write"`.
  - `kix_log_records_total{level}` via a tiny counting log handler — makes "ERROR rate > 0"
    alertable through Grafana without log-based metrics.
  - HTTP request count/duration by route and status (simple ASGI middleware or
    `prometheus-fastapi-instrumentator`), enabling the standard 5xx/latency alerts.

**R3 — Grafana alert rules in a `ki-eksperimentering` folder, routed to `entur-pagerduty`.**
Labels `service_name: kix-avvik`, `env`, `severity` on every rule.
- *Available today, zero code:* pod restarts (> 3/15 m), memory > 85 % of limit, pod not
  ready 3 m — straight from the alerting guide's PromQL examples with
  `namespace="kix-avvik"`, `prometheus_group="kub-ent-prd-001"`.
- *After R1:* readiness-failing alert becomes the poller-death alert for free.
- *After R2:* poller staleness (`time() - kix_poller_last_cycle_timestamp_seconds > 1800`,
  warning — upstream SIRI-SX moves every ~3 min at p50, so 30 min of silence is anomalous
  during service hours), push error ratio, LLM `error` ratio (a sustained Vertex quota
  collision between /meldinger replays and the poller is a known risk, CLAUDE.md), 5xx rate,
  p99 latency.
- Deliberately **no** alert on model-quality signals (precision, verdict mix) — those are
  `/historikk`'s job and move for non-operational reasons.

**R4 — Detect scheduled-query failure in-app.** (small)
The transfer configs are hand-registered and hold SQL copies, so alert on the *outcome*, not
the mechanism: once per poller cycle (or daily), check
`MAX(labelled_at)`/freshness of `disruptions.varsel_decision_outcomes`, and log a structured
ERROR (`event="labelling_stale"`) when it exceeds ~2 days on a weekday. This catches every
documented failure mode — config deleted, SQL-copy divergence, schema breakage — well inside
the 10-day unlabelled-forever window, and lands in the ERROR channel that R2/R3 make
alertable. (Optionally also set `--notification_pubsub_topic` on the transfer configs, but
the in-app check is the one that survives re-registration mistakes.)

### P1 — early in the ramp

**R5 — Log hygiene.**
- Silence `/health` in the access log (a logging filter on `uvicorn.access`, mirroring the
  golden path's `/actuator/**` exclusion). Saves ~35 k INFO entries/day/env and the reader's
  attention.
- `reisevalg_baselines_unavailable`: log once at startup (or at INFO with a much longer
  re-log interval) in environments where the absence is expected. The WARNING channel should
  mean "somebody should eventually look".
- Fold the web-push failure detail (status/host/body) into `event="push"` `result="error"`
  fields so the audit trail is symmetric.
- Add `LOG_LEVEL` env support in `logging_setup.py`. Then either make
  `VARSEL_LLM_LOG_PROMPTS` work as documented or delete it — today it is a dead switch, and
  note that *making it work* starts writing traveller origin/destination prompts to dev Cloud
  Logging, which deserves a conscious decision rather than a side effect.
- A small `test_logging_setup.py` pinning the JSON contract (keys, severity mapping,
  exception-in-one-entry, reserved keys).

**R6 — Post-deploy smoke check in `cd.yml`.** After the gha-helm step: poll `/health` until
ready, assert `GET /<app>-api/config` returns the expected environment label, and assert the
`<script src>` hash referenced by the served `/varsel` `index.html` exists under `/assets/`
(the 2026-08-13 lesson, automated). Fail the workflow loudly — deploys are currently
fire-and-forget.

**R7 — Uptime check on `kix-avvik.entur.io`** (Terraform
`google_monitoring_uptime_check_config` in this repo, or a Grafana synthetic if the team
prefers one pane): the only detector for ingress/DNS/TLS/LB failures, which no in-pod signal
can see. Point it at `/health` so R1 makes it a poller check too.

### P2 — nice to have, not ramp-blocking

- **Readiness split from liveness** once there is something readiness can meaningfully say
  (e.g. initial caches loaded) — today the startup probe covers that window adequately.
- **Request-ID middleware** (accept/generate `X-Request-ID`, include in log fields) — cheap
  correlation without full tracing.
- **OpenTelemetry tracing: proposed deviation.** The golden path recommends it, but this is a
  single service with no service-to-service hops, one background thread, and BigQuery
  dominating every latency profile (~97 % of cycle time, already measured per-phase by
  `poller_phase`). Tracing would add a dependency and per-request overhead to reconstruct what
  the phase logs already say. Recommendation: document the deviation (this section is that
  record) and revisit if a second service or synchronous upstream dependency appears.
- **Client-error reporting for `/historikk`, `/meldinger`, `/demo`** — reuse the `/varsel`
  pattern if these pages get real audiences; they are internal tools today.

### Explicitly out of scope / accepted as-is

- **`forceReplicas: 1`** stays (in-process cache + single poller, documented in
  CLAUDE.md/values.yaml). Ramp implication to accept knowingly: Recreate strategy means a
  brief outage per deploy, and restart (R1) is the only self-healing we have. If the ramp ever
  demands zero-downtime deploys, that is an architecture change (external cache/lease), not a
  monitoring one.
- **SLODash / formal SLOs** — this is an experiment without an SLA; revisit if it graduates.
